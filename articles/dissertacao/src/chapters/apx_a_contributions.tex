\begin{description}
  \item[The fold partition.] Folds are built by
        \path{src/data/folds.py}, which calls scikit-learn's
        \texttt{StratifiedGroupKFold} with five splits, shuffling enabled, and the run's
        seed as the partition seed, grouping by user identifier and stratifying on the task
        label. Grouping by user is what makes the split user-disjoint: a user's
        check-ins fall on one side of every fold.
        % CORRECTED 2026-08-04. The author caught this: the sentence said "a fixed partition seed of 42",
        % and both that and the companion claim below were false. Verified three independent ways, all
        % recorded in science/fold_partition_and_seeds.md:
        %   1. src/data/folds.py builds every split with random_state=self.seed (:1159, :1247, :1453).
        %      The literal 42 occurs ONCE in that file, at :1061, as the DEFAULT VALUE of the seed
        %      parameter. scripts/train.py:1874 passes seed=config.seed, which comes from --seed
        %      (:1375-1376). The partition is therefore a function of the seed.
        %   2. The code's own canon guard (scripts/train.py:1961) calls 42 the "development seed" and
        %      states that "Paper-grade numbers require --seed in {0,1,7,100}".
        %   3. The protocol this entry cites points at LANE2_OVERLAP_VALIDATION.md for the
        %      "unpaired-across-seed rule (different fold partitions per arm)", and that file states at
        %      line 75 that partitions "are NOT bit-identical across arms".
        % Measured, with a control: on a synthetic 300-user frame, roughly four users in five land in a
        % different fold when the seed changes, while re-running the same seed reproduces the partition
        % exactly. See probes R13-foldseed and R13-foldseed2.
        The same routine builds the paired multitask folds, where both tasks share one
        user partition so that a user
        cannot reach one task's training data and the other task's validation data in
        the same fold.
  \item[The seeds.] Four seeds, 0, 1, 7, and 100, each repeating the
        five-fold experiment in full, which is the twenty fitted
        models per configuration the chapter reports. The design is recorded in
        \path{docs/studies/closing_data/v17_completion/STATISTICAL_PROTOCOL.md}. A seed
        sets both the random initialization and the partition, so the four seeds draw four
        user partitions rather than repeating one, and the reported intervals cover both
        sources of variation. Four draws sample the variation across user splits without
        characterizing it. Within one seed both models read the same folds, which is what
        the paired comparison requires; the tests pair the per-seed means, so they never
        assume that a given fold of one seed is the same fold of another.
        % CORRECTED 2026-08-04, same finding as the entry above. The old text read "over that one fixed
        % partition ... Only the initialization varies across the four; the folds do not", which inverted
        % the design. Full evidence in science/fold_partition_and_seeds.md §2-§5.
        % THE CORRECTION MAKES THE RESULT STRONGER, WHICH IS WHY IT IS STATED CAREFULLY. The old sentence
        % conceded that the intervals miss split variability; they do not, because each seed resamples the
        % split. A claim that grows on correction earns more scrutiny, not less, so the text adds the
        % bound that four draws SAMPLE that variability rather than characterize it.
        % THE PAIRED TESTS SURVIVE, and the last sentence records why rather than leaving it to be
        % re-derived: pairing the joint model against the dedicated model happens WITHIN a seed, where
        % both arms share one partition, and the reported tests pair per-seed means (n=4), which never
        % requires fold k of seed 0 to be fold k of seed 1. A future analysis that pairs per (seed, fold)
        % across seeds would not be valid under this design.
        % Probes: R13-foldseed3, R13-foldseed4.
  \item[The region-transition prior.] Rebuilt for each fold from that fold's training
        partition alone by
        \path{scripts/build_phase3_per_fold_transitions.sh}, which writes one file per
        fold. Only the external region baseline of Chapter~\ref{ch:mobiwac} consumes
        it; the joint and dedicated models do not.
  \item[The reported scores.] Read at one saved model per fold, the epoch selected on
        validation, which is the joint-best convention: both tasks are read at the same
        checkpoint rather than each at its own best epoch. The post-hoc scorer is
        \path{scripts/closing_data/score_joint_best.py} and its results are collected in
        \path{docs/studies/closing_data/joint_best/JOINT_BEST_RESULTS.md}.
  \item[The significance tests.] The superiority and non-inferiority tests are
        implemented in \path{scripts/closing_data/superiority_wilcoxon.py} and
        \path{scripts/closing_data/region_match_tost.py}. The reported analysis was run
        by \path{m1_stats_n20.py}, with the pre-registered per-fold variant in
        \path{m2_prereg_perfold.py}; both scripts, their console output
        (\path{m1_full_output.txt} and \path{m2_prereg_output.txt}), and the verdict
        tables that Chapter~\ref{ch:mobiwac} quotes sit together in
        \path{docs/studies/closing_data/v17_completion/stats_n20/}.
  \item[The label-history benchmark.] Computed by
        \path{scripts/embedding_eval/autocorrelation_ceiling.py}.
